## 正文

周五晚上十点，一条负面消息开始发酵。周一早上九点，第一份对外声明必须发出去。中间这 59 个小时，是危机公关最贵的时间。

大部分公司在这段时间里做的是「监测」和「等」：等舆情数据、等老板拍板、等法务意见。但我们想问另一个问题：**如果这场危机，在爆发前 72 小时就先被演过一遍呢？**

这就是我们做「危机预演」（Crisis Rehearsal）的起点。

### 一、我们到底做了什么

我们选了 30 起有公开记录的中国企业危机（2018–2026），把每一件都倒回到它爆发前 72 小时。然后，**只给模拟器当时已经公开的信息**——媒体报道、公司公告、社交平台上的讨论——形成一个「信息洁净室」。这一步如果用事后信息，整个回测就变成了作弊。

接下来，7–12 个 AI 角色登场：记者、散户、监管、做空机构、竞争对手、消费者。它们在模拟信息流里互动两轮，产出一份约 8 千字的预演报告：时间线、利益相关方、升级阶梯、前三大风险、决策建议。最后，一个固定的 LLM 评分器把报告的 Top-3 风险和仓库里记录的真实结局逐条对照，打出 0–3 分。

30 起事件，每起跑 3 次，一共 90 次完整运行。同一套种子、同一套评分标准。

### 二、82.2%，以及这个数字必须带的限定

结果：**前三大风险命中率 82.2%，95% 置信区间 78.5–85.9。**

看到这个数字，先别急着兴奋。它有三个必须说清楚的限定：

第一，它是 30 个事件的「事件均值打分」（每件 0–3 分，均值 2.47/3），**不是**二值命中率，更**不是**对下一次危机的概率预测。

第二，90 次运行**不是 90 个独立样本**。统计单元是 30 个事件，重复跑只是为了估计运行噪声。

第三，区间只覆盖抽样与运行随机性，**不含评分器误差**；评分器也还没有做人工校准。

上一版（v0.1）是每个事件跑一次、报 83%。这次重跑三次后是 82.2%，与旧结果的配对差是 −0.02/3（±0.18）——旧结论复现了。这是整个项目里最不刺激、但我们最想写下来的一句话。

### 三、没藏起来的那 17%

重复跑暴露了一个不好看的事实：**只有 5/30（17%）的事件，在三次运行里完全一致。**

同一事件重跑，组内标准差是 0.26/3；而不同事件之间的难度差，组间标准差是 0.30/3。也就是说，**重跑带来的抖动，几乎和「事件本身难度不同」一样大**。

我们自己的稳定性指标 STA 只有 58，自设及格线是 60。**不及格。**这个数字写在 README 里，也写在 `data/repeat_v02/v02_summary.md` 里。

最主要的错误模式是「过度升级」：模型很爱写「监管介入 / 法务追责 / 甩锅供应商」，读起来专业，但真实结局里没发生。在表现最差的 5 个事件里，6 个零分的 Top-3 席位有 5 个属于这一类。

所以我们把交付规则改成了：**同一事件跑 3–5 次，读共识，不看单次最好成绩。** 单跑单事件的分数，是噪声。

### 四、对企业，它到底有什么用

它的价值不在 82.2%，而在它**逼你在危机前把东西做出来**：一份带时间线的 T-72h 信息包、一张利益相关方与升级阶梯图、一份能上会讨论的自包含 HTML 预演报告，以及在预演中提前暴露的分歧——真出事时，分歧往往是最贵的。

对企业和政府场景，它可以离线部署、数据不出域，报告可直接归档。但要说明白：**我们没有客户案例、没有政府案例、也没有任何认证。** 合规文档只是「标准要求映射 + 缺口清单」，不是测评结论。这些在仓库文档里都写清了。

### 五、你可以自己验证

所有证据都在仓库里：90 条评分原始记录、v0.1 基线、失败案例、评分脚本。不需要模型 key，一条命令就能复算：

```bash
pipx install git+https://github.com/yepinggu66/crisis-rehearsal
crh demo --out demo
```

`crh demo` 会校验证据包、复算已发布统计、生成 4 份自包含 HTML 演练档案。全程离线，10 秒内完成。

### 最后

我们把它开源，不是因为它已经足够好，而是因为它足够**可被检验**：数字可复算、失败可查看、方法可反驳。

如果你在公关、IR、风控或应急口，欢迎拿你们真实的事件来挑战这套方法，尤其是它在什么情况下会失效。我们更想要被证伪，而不是被转发。
